## D-001 等待与刷新方式（入库、提问、人工消息）

- **日期与状态**：2026-09-12；已确认。
- **关联**：REQ-002、REQ-003、REQ-004、REQ-006；AC-003、AC-005、AC-008、AC-010、AC-013、AC-015、AC-016、AC-017、AC-019、AC-020、AC-024；API-004、API-005、API-006、API-009、API-010、API-012、API-015、API-017、API-018；`docs/tech-spec.md` §二、§五、§六。
- **问题与体验影响**：入库要跑解析、打标、向量化和抽 FAQ；提问要跑 FAQ 匹配、分类和知识问答；转人工后员工要看到客服是否接入、是否回了话。这三处怎么等，会直接改变「要盯着看多久、能不能先去做别的、客服话多久出现」。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| 方案 A | 上传后在知识库页等到「入库成功」或失败再操作；提问后在对话里等到一整条回复（带来源标记）再继续；转人工后员工端约每 2 秒刷新当前会话，客服端约每 3 秒刷新工单列表。中等文档可能等十几秒到一两分钟；客服回复最多延迟约 2 秒。实现简单，来源标记与整段文字一起出现。 | 同步 HTTP 与短轮询即可；不引入任务队列或 WebSocket。 |
| 方案 B（已选） | 入库提交后可离开，回来看进度；提问时文字逐字出现；客服一发、员工马上看到。等待体验更好，但入库中途刷新要能找回任务；流式时来源标记要先出、正文后出；要实现后台任务和实时通道，失败恢复更复杂。 | 进程内后台任务 + SSE 流式回答 + WebSocket `/ws`。入库进度写入文档记录，离开后再打开列表/详情可回看。 |

- **建议及理由**：当时建议方案 A（实现简单）。用户未采纳建议。
- **最终选择与确认依据**：方案 B。2026-09-12 用户明确选择：希望异步完成；传入文档后可以去看别的事情、切换界面。入库提交后可离开，回来看进度；提问时文字逐字出现；客服一发、员工马上看到。
- **落地与验收**：已写入 tech-spec API-004（接收即返回）、API-005/006（回看进度）、API-017（流式正文）、API-018（人工与工单实时推送）；PRD 已同步受影响 AC。测试尚未执行。
- **复议条件（需要时）**：进程重启导致进行中入库大量失败，或实时通道在目标浏览器不可用。

## D-002 回答质量与调用费用（模型档位 + FAQ 相近松紧）

- **日期与状态**：2026-09-12；已确认。
- **关联**：REQ-002、REQ-007；AC-016、AC-017、AC-018、AC-023；EXT-001、EXT-002；`docs/tech-spec.md` §四、§五 API-010、§七。
- **问题与体验影响**：FAQ 要拦住「原问和意思相近」的问；拦太松会拿错 FAQ，拦太严会漏掉改写问、改走知识问答。模型越强，分类和回答通常更稳，费用和等待也会更高。两者一起决定「答得准不准」和「每次提问大概花多少」。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| 方案 A（已选） | 对话与打标用 `qwen-plus`，向量用 `text-embedding-v3`（1024 维）。FAQ 先做规范化原文匹配，再按向量余弦 ≥ `0.82` 视为相近。相近改写大多能拦住；个别擦边问可能漏到知识问答。费用与质量折中。 | Chat / Embedding 走百炼 OpenAI 兼容接口。来源：[OpenAI 兼容 Chat](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions)、[OpenAI 兼容 Embedding](https://help.aliyun.com/zh/model-studio/embedding-interfaces-compatible-with-openai)。阈值未用本项目语料实测，上线后可只改配置。 |
| 方案 B | 对话改 `qwen-turbo`，FAQ 阈值降到约 `0.72`。更便宜、稍快；闲聊和分类可能更飘，更容易把不相关的问拦成某条 FAQ。 | 同接口，换模型名与阈值。 |
| 方案 C | 对话改更强档（如控制台当前的 Max 系列），FAQ 阈值升到约 `0.88`。分类和知识问答通常更稳，费用更高；很近的改写也可能漏拦。 | 官方示例出现过更新的模型名；具体可用性取决于账号开通情况，不能当作本环境已核实。 |

- **建议及理由**：建议方案 A。能覆盖「原问 + 意思相近」的主路径，又不必一上来用最贵模型。
- **最终选择与确认依据**：方案 A。2026-09-12 用户明确选择：`qwen-plus` + `text-embedding-v3`；FAQ 先原文再相近（阈值 0.82）。
- **落地与验收**：已写入 §七配置默认值 `llm_chat_model`、`llm_embed_model`、`faq_similarity_threshold`。用 AC-016 的原问与改写问、以及一条故意不像的问做对照。测试尚未执行。
- **复议条件（需要时）**：相近问经常漏拦或错拦；或账号未开通 `qwen-plus` / `text-embedding-v3`。

## D-003 会话、原文与工单留存

- **日期与状态**：2026-09-12；已确认。
- **关联**：REQ-003、REQ-005、REQ-006；AC-011、AC-019；API-005～API-009、API-012、API-013；`docs/tech-spec.md` §三、§七。
- **问题与体验影响**：历史会话、上传原文、分块、FAQ、工单要不要一直留在本机，决定以后还能不能翻到当时的问答，以及磁盘会积多少文件。本次没有删除或清理界面。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| 方案 A（已选） | 成功入库的原文、分块、FAQ、会话、工单都长期放在本机 SQLite 与 `backend/data/`，不自动过期、不提供删除。历史可以一直打开；磁盘占用随使用增加。单账号内部使用，无跨人隔离。 | PRD 要求能看历史和入库结果，未要求清理。 |
| 方案 B | 会话或原文按固定天数自动删（例如 90 天）。更省空间；超期后历史和部分入库结果打不开，客服也看不到旧工单上下文。 | 需要定时清理；与「打开历史看到当时内容」可能冲突，要改验收。 |

- **建议及理由**：建议方案 A。本次范围没有清理或删除，先把历史和入库结果留住。
- **最终选择与确认依据**：方案 A。2026-09-12 用户明确选择：成功入库的原文、会话、工单长期放本机，不自动删。
- **落地与验收**：无删除接口、无定时清理；失败入库不把原文当成功件长期保留。用 AC-011、AC-019 验证历史和成功入库结果可再次打开。测试尚未执行。
- **复议条件（需要时）**：磁盘压力变大，或后续明确要求删除/脱敏。
